Resumen

Este artículo analiza el uso básico de Git para organizar cambios en un proyecto de software. El objetivo es comprobar cómo los commits y las ramas permiten conservar versiones e identificar modificaciones incompatibles. Se revisó la documentación oficial y se realizó una prueba local con un archivo de texto, dos ramas y cambios sobre una misma línea. Se registraron cuatro commits y un conflicto de integración, resuelto mediante edición manual. Los resultados muestran que el historial conserva ambas líneas de trabajo, aunque la elección del contenido final requiere intervención humana. Se recomienda registrar cambios pequeños y revisar las diferencias antes de integrarlos.

Palabras clave: commits; control de versiones; git; integración; ramas

I. Introducción

Guardar archivos como «final» y «final-corregido» dificulta reconocer qué cambió. Un repositorio de Git ofrece una alternativa para registrar el trabajo; el comando git init permite crearlo localmente [1]. El objetivo de este artículo es comprobar cómo Git registra versiones y detecta un conflicto entre dos ramas. Esta práctica resulta útil para comprender situaciones comunes en proyectos universitarios.

II. Marco teórico

A. Preparación y registro de cambios

Git distingue entre los archivos de trabajo y el área de preparación. El comando git add incorpora al índice el contenido que se desea registrar [2]. Después, git commit crea una confirmación con el contenido preparado y un mensaje descriptivo [3]. Por eso, guardar un archivo en el editor no equivale a registrar una versión.

B. Ramas e integración

Las ramas permiten mantener líneas de trabajo diferentes; git branch sirve para crearlas y consultarlas [4]. Para incorporar cambios de otra rama se utiliza git merge. Cuando existen modificaciones incompatibles, la integración puede detenerse y requerir una resolución manual [5].

III. Metodología o desarrollo

Se realizó una prueba local con Git 2.51.1 y el archivo saludo.txt, sin repositorio remoto. El procedimiento fue:

  1. Crear la rama main, escribir «Hola» y registrar el primer commit.
  2. Crear la rama mejora, cambiar el texto a «Hola, equipo» y confirmar.
  3. Volver a main, escribir «Hola, clase» y registrar otro commit.
  4. Ejecutar git merge mejora y comprobar el conflicto.
  5. Resolver con «Hola, equipo de clase», preparar el archivo y confirmar la integración.

Se revisaron tres indicadores:

  • Cantidad de ramas conservadas.
  • Cantidad de commits en el historial final.
  • Archivos en conflicto y estado posterior a la resolución.

IV. Resultados y discusión

Tabla I. Resultados de la prueba local
Indicador Resultado Comprobación
Ramas conservadas 2 git branch
Commits finales 4 git rev-list --count HEAD
Archivos en conflicto 1 git status durante la integración
Cambios pendientes al terminar 0 git status --porcelain

El cuarto commit corresponde a la resolución de la integración. El conflicto mostró que Git no podía elegir automáticamente entre dos saludos distintos sobre la misma línea. Tras editar el archivo, el historial conservó los cambios de ambas ramas. Estos resultados describen únicamente una prueba pequeña: no permiten medir productividad, tiempos de trabajo ni comportamiento de equipos grandes.

V. Conclusiones

Se cumplió el objetivo al registrar versiones y provocar un conflicto controlado. Git mantuvo el historial, mientras que la decisión sobre el saludo final fue manual. Se recomienda confirmar cambios pequeños y descriptivos. Como continuación, conviene repetir la prueba con varios archivos y colaboradores para analizar situaciones de integración más variadas.
